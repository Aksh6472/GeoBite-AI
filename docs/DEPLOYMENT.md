# Deployment

## Live on Vercel (current)

`vercel.json` deploys one Vercel project with two **Services** on the same domain: `frontend/` (Next.js) and `backend/` (FastAPI, `app.main:app`). Requests to `/api/*` go to FastAPI; everything else goes to Next.js, so the auth cookie stays first-party. The database is **Neon Postgres** (Vercel Marketplace, connected with prefix `DATABASE`, so the app reads `DATABASE_URL`). Community photos are stored in Postgres because Vercel has no persistent disk.

Project environment variables: `ENVIRONMENT=production`, `JWT_SECRET`, `IP_HASH_SALT`, `COOKIE_SECURE=true`, `TRUST_PROXY=true`, `CORS_ORIGINS=<site URL>`, plus `DATABASE_URL` from Neon.

**Migrations and seed** (no shell on Vercel): call the protected bootstrap endpoint after a deploy that adds a migration. It is idempotent and only seeds an empty database.
```bash
TOKEN=$(python3 -c "import hmac,hashlib,os;print(hmac.new(os.environ['JWT_SECRET'].encode(),b'geobite-bootstrap',hashlib.sha256).hexdigest())")
curl -X POST https://<site>/api/system/bootstrap -H "X-Bootstrap-Token: $TOKEN"
```
Every `git push` to `main` redeploys. Limits: the in-memory rate limiter is per function instance, and Hobby plans are for non-commercial use.

## Go live on Render (recommended, one-click Blueprint)

The repository includes `render.yaml`, which creates:
- **`geobite-db`**: managed PostgreSQL (PostGIS is enabled automatically by the migrations).
- **`geobite-ai`**: one web service built from `deploy/Dockerfile`. A single container runs Next.js on `$PORT` and proxies `/api/*` to FastAPI on `127.0.0.1:8000`. On every start it applies migrations; on the first start it seeds the labelled synthetic demo data.

Secrets (`JWT_SECRET`, `IP_HASH_SALT`) are generated by Render and never stored in the repository.

**Steps**
1. Push this repository to GitHub (a private repository is fine):
   ```bash
   # create an empty repository on github.com first (no README), then:
   git remote add origin https://github.com/<you>/geobite-ai.git
   git push -u origin main
   ```
2. On https://dashboard.render.com choose **New > Blueprint**, connect GitHub and select the repository.
3. Render reads `render.yaml`. Click **Apply**. The first build takes about 8-12 minutes.
4. Open `https://geobite-ai.onrender.com` (Render shows the exact URL; if the name is taken it adds a suffix, so update `CORS_ORIGINS` to match).
5. Sign in with the demo accounts, or register your own account at `/register`. Everything you enter is stored in the Render database.

**Free-plan limits:** the web service sleeps after 15 minutes without traffic (the next visit takes about a minute to wake), the free database **expires after 30 days**, and uploaded photos are kept on the container disk, so they are lost on redeploy. For a lasting demo, upgrade the database to `basic-256mb` and the service to `starter`, and add a Render Disk mounted at `/app/backend/uploads`.

**After a public demo:** set `SEED_ON_START=false` once real users begin entering data, and never enter real patient data without the approvals listed in `SECURITY_ETHICS.md`.

**Updating:** every `git push` to `main` redeploys automatically. Migrations run on start, and seeding is skipped when data exists.

## Containers

| Image | Build | Notes |
|---|---|---|
| `api` | `backend/Dockerfile` (python:3.12-slim, non-root) | On start: `alembic upgrade head`, an optional seed (`SEED_ON_START`), then Uvicorn with 2 workers and `--proxy-headers` |
| `web` | `frontend/Dockerfile` (multi-stage, Next.js `standalone`, non-root) | `API_INTERNAL_URL` must point at the API (default `http://api:8000`) |
| `db` | `postgis/postgis:16-3.4` | Use a managed PostGIS in production (e.g. RDS or Cloud SQL with PostGIS enabled) |

```bash
cp .env.example .env     # set secrets
docker compose up --build -d
docker compose logs -f api
```

## Production checklist
- [ ] `ENVIRONMENT=production`, a strong `JWT_SECRET` (`openssl rand -hex 32`) and `IP_HASH_SALT`.
- [ ] `SEED_ON_START=false`, so the production database has no synthetic data.
- [ ] TLS terminated at a load balancer or reverse proxy; `COOKIE_SECURE=true`.
- [ ] Expose **only the web service** publicly. Keep the API private behind it (`TRUST_PROXY=true` is only safe then).
- [ ] `CORS_ORIGINS` set to the public origin.
- [ ] Persistent volume or object storage for `UPLOAD_DIR`.
- [ ] Daily `python -m app.maintenance purge` (cron, Kubernetes CronJob or a scheduled task).
- [ ] Optional scheduled `POST /api/alerts/evaluate` and `POST /api/analytics/hotspots/run` (e.g. nightly) with an admin service token.
- [ ] Database backups and point-in-time recovery; restrict DB network access.
- [ ] Redis-backed rate limiting if running more than one API replica (`ratelimit.py` exposes a small interface to swap).
- [ ] Tile server: the default uses `tile.openstreetmap.org`, which suits demonstrations only. Set `NEXT_PUBLIC_TILE_URL` to your own or a commercial tile service for production traffic (OSM tile usage policy).
- [ ] Health check: `GET /api/health` (checks DB connectivity).

## Database migrations

```bash
cd backend
alembic upgrade head                     # apply
alembic revision --autogenerate -m "..." # create after editing models.py
alembic downgrade -1                     # roll back one
```
Migration `0002` is PostgreSQL-only (PostGIS columns, triggers, GIST indexes) and is a no-op on SQLite.

## Seed data

```bash
python seed.py           # only if empty
python seed.py --reset   # wipe ALL data and re-seed (development only)
```
The seed generates about 3,000 bite incidents over 18 months, ~760 community reports, vaccination records, and rule-generated alerts with a partially progressed workflow. It also runs one hotspot analysis and one model training. Everything is flagged synthetic.

## Logs and observability
The API logs one JSON-style line per request (method, path, status, latency, request ID). Every response carries `X-Request-ID`, which matches error responses to log lines.
